# حسابیار — بکند MVP

بکند ساده و مستقل (Node.js + Express + SQLite) برای پنل حسابیار، با API کامل CRUD
برای مشتریان/محصولات/فاکتورها/پرداخت‌ها + ماژول یکپارچه‌سازی با **هلو (Firebird)**.

## اجرا در محیط توسعه

```bash
npm install
cp .env.example .env
npm run dev       # سرور روی پورت 4000 بالا میاد
npm run seed      # ساخت کاربر پیش‌فرض owner@hesabyar.local / 123456
```

## بالا آوردن روی هاست رایگان

این پروژه با **Render.com (Free Web Service)** تست شده (فایل `render.yaml` آماده‌ست):

1. پروژه رو در یک ریپوی گیت‌هاب پوش کن (فقط پوشه `hesabyar-backend`).
2. توی Render یک "New Web Service" بساز و ریپو رو وصل کن؛ Render خودش `render.yaml` رو می‌خونه.
3. چون SQLite فایلیه، حتما یک **Persistent Disk** وصل باشه (در `render.yaml` این کار شده)
   وگرنه هر بار deploy جدید، دیتابیس پاک میشه.
4. بعد از بالا اومدن، آدرس `https://<app-name>.onrender.com/api/health` باید `{status:"ok"}` برگردونه.

جایگزین‌های رایگان دیگه که همین ساختار روشون کار می‌کنه: **Railway (Free trial)**،
**Fly.io (free allowance)**. نکته مشترک همه: باید یک دیسک/volume persistent برای
فایل SQLite در نظر بگیری، وگرنه دیتا با هر ریستارت از بین میره.

> نکته: Vercel/Netlify برای این بکند مناسب نیستن چون serverless هستن و فایل SQLite
> رو persist نمی‌کنن. Render یا Railway (که یک process همیشه روشن اجرا می‌کنن) گزینه درستن.

## اتصال فرانت به این بکند

در فرانت (`hesabyar`)، فقط کافیه یک `VITE_API_URL` ست بشه (مثلا در `.env` فرانت):

```
VITE_API_URL=https://hesabyar-backend.onrender.com/api
```

و لایه‌ی fetch/axios فرانت به‌جای mockData به این API وصل بشه (این بخش رو در قدم بعد،
وقتی صفحات فرانت رو تکمیل کنیم، سیم‌کشی می‌کنیم).

## ⚠️ نکته مهم درباره‌ی یکپارچگی با هلو (باید حتما بدونی)

هلو معمولاً یک نرم‌افزار **دسکتاپ محلی** روی یک سیستم/سرور در دفتر مشتریه که از
دیتابیس **Firebird** (فایل `.FDB`) استفاده می‌کنه. این بکند که روی هاست رایگان/ابری
(Render و امثالش) اجرا میشه، **به‌صورت پیش‌فرض به شبکه‌ی داخلی مشتری دسترسی نداره**.
برای این‌که «خواندن و نوشتن دوطرفه با دیتابیس هلو» واقعا کار کنه، یکی از این سه راه لازمه:

1. **آپلود فایل بکاپ هلو (.FDB/.bak)** — مشتری بکاپشو از هلو می‌گیره و توی پنل
   آپلود می‌کنه؛ بکند اون فایل رو با `node-firebird` باز می‌کنه، می‌خونه، map
   می‌کنه به جداول حسابیار. **این حالت الان در `/api/holo/import` پیاده شده** و
   روی هاست رایگان هم کار می‌کنه چون فقط یک فایل آپلودیه، نیازی به اتصال شبکه به
   سیستم مشتری نداره. (نوشتن به همون فایل هم ممکنه، ولی export مستقیم به سیستم
   زنده‌ی مشتری نه.)
2. **اتصال زنده روی شبکه محلی/VPN** — اگه سرویس Firebird مشتری (پورت 3050) از
   طریق VPN یا port-forward در دسترس اینترنت باشه، بکند می‌تونه مستقیم بهش وصل
   بشه (`/api/holo/export` این حالت رو پیاده کرده). امنیتی نیست برای production
   ولی برای MVP/تست قابل استفاده‌ست.
3. **Agent محلی (پیشنهاد اصلی برای فاز بعد)** — یک اسکریپت کوچیک روی همون سیستم
   هلو نصب میشه، به فایل .FDB محلی وصل میشه، و از طریق یک API امن (HTTPS) با
   بکند حسابیار sync می‌کنه (push/pull). این امن‌ترین و قابل‌اتکاترین روش برای
   production هست ولی نیاز به نصب یک برنامه‌ی کوچیک روی سیستم مشتری داره.

**برای MVP فعلی، مسیر ۱ (آپلود فایل بکاپ) پیاده‌سازی و آماده‌ست** — چون تنها
مسیریه که بدون هیچ زیرساخت اضافه (VPN و غیره) روی هاست رایگان کار می‌کنه.
اسکیمای نگاشت جداول (`src/lib/holoSchema.js`) بر اساس ساختار عمومی هلوئه و باید
بعد از گرفتن یک بکاپ واقعی از مشتری verify بشه (اسم دقیق فیلدها بین نسخه‌های
مختلف هلو (استاندارد/طلایی/۱/۲) فرق می‌کنه).

## API خلاصه

| Method | Path                | توضیح |
|---|---|---|
| POST | `/api/auth/register` | ثبت‌نام |
| POST | `/api/auth/login` | ورود، برمی‌گردونه JWT |
| GET/POST | `/api/clients` | لیست/ساخت مشتری |
| GET/PUT/DELETE | `/api/clients/:id` | مشتری |
| همین الگو برای | `/api/products`, `/api/invoices`, `/api/payments` |
| GET | `/api/holo/tables` | لیست جداول هلو و نگاشتشون |
| POST | `/api/holo/import` | آپلود فایل .FDB یا اتصال زنده → import به حسابیار |
| POST | `/api/holo/export` | حسابیار → نوشتن روی دیتابیس هلو (اتصال زنده) |
| GET | `/api/holo/log` | تاریخچه sync |

همه‌ی مسیرها (به‌جز `/auth` و `/health`) نیاز به هدر دارن:
`Authorization: Bearer <token>`

## راه‌اندازی ایمیل واقعی (SMTP)

زیرساخت ارسال ایمیل (`src/lib/mailer.js`) کامل پیاده‌سازی شده و همین الان به دو
جریان واقعی وصله:
- **فراموشی رمز عبور** (`POST /api/auth/forgot-password` → لینک بازنشانی)
- **دعوت کاربر جدید به شرکت** (`POST /api/company-users` → ایمیل کاربر + رمز موقت)
- **یادآوری سررسید فاکتور** (فاز ۵ — `src/lib/invoiceReminders.js`)

تا وقتی متغیرهای `SMTP_*` در `.env` خالی باشن، به‌جای ارسال واقعی، محتوای ایمیل
توی کنسول سرور چاپ می‌شه (مناسب توسعه/تست، بدون نیاز به SMTP واقعی). برای فعال
کردن ارسال واقعی:

1. یک سرویس SMTP بگیر. گزینه‌های رایج:
   - **Resend** (resend.com) — رایگان تا ۳۰۰۰ ایمیل/ماه، ساده‌ترین راه‌اندازی
   - **SendGrid** (sendgrid.com) — رایگان تا ۱۰۰ ایمیل/روز
   - **Gmail** با App Password (فقط برای تست/MVP کوچیک، نه production جدی)
2. مقادیر زیر رو در `.env` (کنار `SMTP_HOST` و بقیه که همین الان توی `.env.example` هست) پر کن:
   ```
   SMTP_HOST=smtp.resend.com          # یا هر میزبان دیگه
   SMTP_PORT=587
   SMTP_USER=resend                   # یا API key/یوزرنیم سرویس مربوطه
   SMTP_PASS=xxxxxxxxxxxx
   SMTP_FROM="حسابیار <no-reply@yourdomain.com>"
   ```
3. سرور رو دوباره بالا بیار. توی لاگ استارتاپ، خودش وضعیت اتصال رو چک و چاپ
   می‌کنه (✅ وصل شد / ⚠️ خطای اتصال / ⚠️ اصلاً تنظیم نشده).
4. برای چک‌کردن دستی هر وقت (بدون ریستارت سرور)، از کاربر لاگین‌شده:
   `GET /api/company/mail-status` → `{ configured, ok, error? }`

**نکته:** این وضعیت («کد کامله، فقط نیاز به credential واقعیه») با یه گپ کد فرق
داره — تنظیم `.env` production یه تصمیم عملیاتی (انتخاب سرویس، دامنه‌ی
فرستنده و غیره) است که فقط صاحب پروژه می‌تونه بگیره.
